# ADR-002：大文件传输的自适应设计（体积 × 网络）

- 状态：**待决策**（本文件只做方案与取舍，不含实现）
- 日期：2026-11-06
- 前置数据：本文所有"实测"均来自本机（Ryzen 9 9950X3D / 32 逻辑核 / NVMe / 回环），
  release 构建，见 `hub_concurrency_probe`、`perf_probe` 与 ETW/微基准归因。

## 1. 问题陈述

需求：**大文件传输要在公网和局域网都自适应**，用户不配置。

现状实测（release，64/256 MiB 单文件，K 个 peer 并发拉取）：

| 场景 | 吞吐 | 对照基线 |
|---|---|---|
| K=1（单设备对单设备） | 154~189 MiB/s | 纯 QUIC 单连接 **195** → 我们已达 **97%** |
| K=2 | 266~288 | 纯 QUIC 双连接 **321**（86~90%） |
| K=4 | 388~393 | 纯 QUIC 四连接 **402~478**（92~96%） |
| 本机 SHA-256 | 2551 MiB/s（release）/ 53 MiB/s（debug） | 哈希占 release CPU 约 7~9% |
| 本机磁盘写 / 读 | 2751 / 4752 MiB/s | 接收端 100~190 MiB/s，占 <5% |
| fsync | 740 MiB/s | 当前**接收端不做 fsync** |

结论：**局域网内应用已到传输上限**；余量来自三处结构性限制：

1. **所有传输共用一条 QUIC 双向流**（控制与数据在同一 `FramedRead/Write` 上，帧严格有序）
   → 单流窗口 + 队头阻塞，无法并行；
2. **`stream_receive_window` 用 quinn 默认 1.25 MB** → 100 ms RTT 下单流上限约 **12.5 MiB/s**；
3. **每设备只有一条 QUIC 连接** → 单设备天花板 ≈ 195 MiB/s，而 4 条连接可达 400+。

## 2. 目标与非目标

**目标**
- 用户零配置：按文件体积 + 实测 RTT/吞吐自动选择分块、并发流数、连接数、落盘策略。
- 公网单文件吞吐达到"可用带宽"的绝大部分（目标 ≥70% 的 BDP 上限）。
- 局域网不退化（保持 ≥90% 现有 189 MiB/s 单设备吞吐）。
- 失败可续传：任一子流失败不影响整体，按偏移重试。

**非目标**
- 不做跨设备分片（同一个文件的多个子流仍来自同一来源设备）。
- 不改加密/认证模型。
- 不追求 WAN 上超过单链路物理带宽。

## 3. 关键设计：把"一条流"拆成"控制面 + 数据面"

### 3.1 现状问题
`CBFrame` 的 `Data` 帧与控制帧共用一条流 → 任何一块的背压都会影响所有传输（P3 已把
actor 主循环解耦，但**单流有序**这一物理限制仍在）。

### 3.2 目标形态
```
控制流（每设备 1 条，bidi，长期存在）
  ContentGet / ContentBegin / ContentEnd / ContentCancel / 元数据 / 心跳
数据流（每传输 1~N 条，bidi，短生命周期）
  [TransferHeader{req_id,item_id,file_id,offset,length,sha256}] → Data* → FIN
```

- 每条数据流只承载一个子区间（`offset + length`），接收端 `accept_bi()` 后起独立 writer task。
- 控制流不再承载 `Data` 帧；`ContentBegin` 只做元数据登记，真正数据走新开流。
- 需要 `PROTOCOL_VERSION += 1`（我们两端同版本部署，且已有版本闸门）。

**收益**：天然并行、每流独立窗口、子流失败可单独重试、控制面不被数据阻塞。

### 3.3 子流数量（并发度）自适应
设文件大小 `S`，实测 RTT `r`，单流实测吞吐 `t1`：

| 条件 | 子流数 |
|---|---|
| `S < 8 MiB` | 1（开销不值得） |
| `r < 20 ms`（LAN） | 1（单流已到 195 MiB/s，拆分收益 <10%，实测 4 流同连接反而 190） |
| `20 ms ≤ r < 80 ms` | 2 |
| `r ≥ 80 ms`（WAN） | 3~4，且若 `t1 × N` 仍明显低于链路估计带宽，继续加到上限 6 |
| 任一子流连续 3 次超时/重传激增 | 降 1（AIMD 式，带 30 s 冷却） |

控制器原则：**只在 WAN 启用多流**，LAN 保持单流以避免额外内存与调度开销；每次调
整后观察 5 s 再决定下一步（带滞回，避免抖动）。

### 3.4 窗口与 BDP
`quinn` 的窗口是**连接级固定配置**，不能在传输中按流调整。方案：

- 连接建立时按**首次 RTT 探测**（握手完成后的 `rtt()`）分两档配置：
  - `rtt < 20 ms` → `stream_receive_window = 1.25 MB`（现状，省内存）
  - `rtt ≥ 20 ms` → `stream_receive_window = 8 MB`、`receive_window = 64 MB`、`send_window = 32 MB`
- 8 MB/100 ms → 单流上限约 **80 MiB/s**；配合 4 条子流可覆盖 ~300 MiB/s 的 WAN 链路。
- 内存代价：按 4 条子流 × 8 MB ≈ 32 MB/连接（仅 WAN 档）。

### 3.5 分块大小自适应
| 档 | 条件 | 块大小 |
|---|---|---|
| LAN | rtt < 20 ms | 64 KiB（现状） |
| 中距 | 20~80 ms | 256 KiB |
| WAN | ≥ 80 ms | 512 KiB（上限 1 MiB，受 10 MiB 帧上限与在途预算约束） |

依据：实测 64 KiB→1 MiB 在回环上仅 +4~12%，但 WAN 上块越小，每块一次
`write_all().await` 的往返开销占比越高；512 KiB 是收益/内存的折中。
**在途字节预算**（当前 12 MiB/接收者）随块大小上调到 `max(12 MiB, 4×块大小)`，
并发 8 路时最坏约 100 MiB。

### 3.6 多连接（仅 WAN + 超大文件）
当 `S ≥ 256 MiB` 且 `rtt ≥ 40 ms` 且单连接实测吞吐 < 链路估计的 60% 时，允许为**同一条
传输**开第 2 条 QUIC 连接（对端已有监听，无需新协议）。
- 收益依据：纯 QUIC 2 连接 321 vs 1 连接 195 MiB/s（+64%）。
- 风险：认证/TOFU 复用同一设备证书即可；连接生命周期管理更复杂。
- **列为第三阶段**，前两阶段不实现。

### 3.7 落盘与持久性策略
当前接收端不做 fsync（性能好，但崩溃可能丢"已完成"数据）。按体积分流：

| 文件体积 | 策略 |
|---|---|
| < 8 MiB（含所有文本/小图） | `ContentEnd` 前 `sync_all()`（成本毫秒级，保证完成即持久） |
| ≥ 8 MiB | 先 `rename` 提交（原子可见），**后台**对已完成文件做 `sync_data`；DB 标记 `durable=pending`，完成后置 `durable` |
| 用户可配 | `CB_FSYNC_POLICY=always|large-only(默认)|never` |

理由：大文件同步 fsync 会引入秒级尾延迟（740 MiB/s 的 flush 带宽），而后台补齐兼顾
安全与吞吐。

### 3.8 续传
`ContentGet{offset}` 已存在；改为每子流携带 `(offset,length)`，失败子流按"已完成字节
数"重新开流续传，最多重试 3 次后降级为单流重传该区间。

## 4. 闭环自适应控制器（取代静态网络档位）

**原则：不猜网络，测出来再收敛。** 上面 3.3/3.5 的 RTT 分档只作为**冷启动默认值**；
真正决定并发流数、连接数与分块的是传输过程中实时测得的信号。

### 4.1 可观测信号（全部来自 `quinn`，无需额外探测包）

| 信号 | 来源 | 用途 |
|---|---|---|
| 平滑 RTT `srtt` / 抖动 | `Connection::stats().path.srtt` | 计算 BDP、判定拥塞 |
| 单流 goodput | 应用侧窗口计数（每 200 ms 统计） | 判断"加流是否还有收益" |
| 丢包/重传率 | `stats().path.lost_packets` 增量 | 拥塞退缩 |
| 发送阻塞占比 | `send_stall` 计数（`write_all` 等待超过 `srtt` 的比例） | 判断发送窗口是否饱和（该加连接/加流） |
| 每块写入耗时 | 接收端 `write_all` 计时 | 判断磁盘是否成为瓶颈（决定是否降分块） |

> 这些信号在 P3 之后已经分散存在（进度事件、`send_data_chunk` 的超时包装）；控制器
> 只需要聚合成一个 200 ms 的统计窗口，**不增加网络流量**。

### 4.2 并发流数控制器（AIMD + 探针）

```
N = profile.streams or 1            # 冷启动 1
每 T = clamp(4×srtt, 300ms, 2s) 评估一次窗口 goodput g：
  if 还有余量(S_remaining > 16 MiB) and N < 6:
      N += 1                        # 探针：加一条流
      观察下一个 T：
         gain = (g_new - g_old) / g_old
         if gain > 8%: 接受（继续探）
         else:         回退 N -= 1，标记 ceiling_reached（本传输不再探）
  if 丢包 > 1% or srtt > 2.5×srtt_base:
      N = max(1, N-1); chunk = max(64KiB, chunk/2); 冷却 2×T
  if 发送阻塞占比 > 40% and N < 6:
      N += 1                        # 发送窗饱和 → 加流
```

- **LAN 会自动停在 N=1**：回环实测 4 条流同连接 190 vs 单流 195 MiB/s，加流无收益 →
  探针 1 次即回退（代价 ~1 s，可在 32 MiB 以上文件才启用探针来摊薄）。
- **WAN 会自动爬升**：每加一条流若收益 >8% 就继续，直到收益消失或触发丢包退缩。
- **滞回**：每次决策后至少等一个窗口；`ceiling_reached` 后本传输不再上探，避免抖动。

### 4.3 连接数控制器（仅超大文件）

单连接内 4 条流仍受**连接级**发送窗口与 UDP 单流处理限制（实测 4 流同连接 190，
4 连接 402~478 MiB/s）。因此：

```
if S_remaining > 256 MiB and 发送阻塞占比 > 40% and 连接数 < 2:
    开第 2 条 QUIC 连接（同设备证书，复用监听）
    观察一个窗口：聚合 goodput 提升 > 15% ? 保留 : 关闭并标记 ceiling
```

- 只在"流已经加满仍被连接级限制"时才开新连接，避免无意义的多连接开销；
- 上限 2 条（实测 2→4 连接收益递减，且内存/CPU 成本上升）。

### 4.4 分块控制器（BDP 驱动）

```
目标：任意时刻在途 ≥ 8 块
chunk = clamp(goodput × srtt / 8, 64 KiB, 1 MiB)
```

- 每 2 个窗口更新一次，按 2 的幂取整（64/128/256/512/1024 KiB），避免频繁抖动；
- 若接收端"每块写入耗时" > 80% 的块发送间隔 → 说明磁盘/CPU 吃紧，**不增大**分块；
- 依据：BDP 决定需要多少字节"在途"才能填满管道；固定 64 KiB 在 100 ms RTT、
  200 MiB/s 的链路上只有 6.4 MiB 在途，接近 1.25 MB 默认窗口的 5 倍——必须配合 3.4
  的大窗口才有意义。

### 4.5 窗口：连接建立时一次性决定

`quinn` 的窗口是连接级配置，传输中不能改。方案改为**按握手 `srtt` 直接给足**：

| `srtt` | `stream_receive_window` | `receive_window` | `send_window` |
|---|---|---|---|
| < 20 ms | 2 MiB | 16 MiB | 16 MiB |
| ≥ 20 ms | 8 MiB | 64 MiB | 32 MiB |

内存代价：WAN 档 4 流 × 8 MiB ≈ 32 MiB/连接，上限 2 连接 ≈ 64 MiB；LAN 档约 8 MiB。
比"猜错档位后整个传输被 BDP 卡死"划算。

### 4.6 每 peer 画像（热启动）

控制器把结果写入 `peer_profile` 表（peer_id, streams, chunk, connections, srtt_class,
confidence, updated_ts），下次对同一设备直接以该值起步（跳过探针的 1~2 个窗口），
并每 7 天或检测到 `srtt_class` 变化时衰减为冷启动值。

### 4.7 稳定性与安全约束

- **永不**让并发超过 6 流 / 2 连接 / 在途 > 128 MiB；
- 探针只在剩余 > 16 MiB 时启用（小文件直接用画像或默认值）；
- 控制面优先级：若 `list_peers`/心跳的 p99 超过 50 ms，立即回退一档（保护交互）；
- 所有决策打点（`transfer.adapt{old,new,reason,gain}`），便于事后解释"为什么慢"。

### 4.8 冷启动默认值（原矩阵降级为默认）

| 体积 \ 网络 | `srtt` < 20 ms | ≥ 20 ms |
|---|---|---|
| < 8 MiB | 1 流 / 64 KiB / 同步 fsync | 1 流 / 256 KiB / 同步 fsync |
| ≥ 8 MiB | 1 流 / 64 KiB / 后台 fsync | 2 流 / 512 KiB / 后台 fsync |

之后完全由 4.2~4.5 的控制器接管。

## 5. 分阶段落地

| 阶段 | 内容 | 协议变更 | 风险 | 预期收益 |
|---|---|---|---|---|
| **A** | 连接建立按 `srtt` 设定窗口（4.5）+ fsync 策略（3.7）+ 删除发送端冗余哈希 + worker 4→8 | 无 | 低 | LAN +5~15%；**WAN ×6**（已实测，见 5.1） |
| **A2** | **9000 B jumbo UDP 载荷 + 8 MiB socket 缓冲**（DPLPMTUD 自动探测、黑洞回退） | 无 | 中（需路径支持 jumbo） | **LAN 单设备 ×3**（已实测，见 5.3） |
| **B** | 控制面/数据面分离（3.2）+ 每传输独立流 + 数控制器（4.2）+ per-peer 画像（4.6） | `PROTOCOL_VERSION += 1` | 中 | WAN 再 ×2~4，LAN 不退化 |
| **C** | 多连接/多 Endpoint（4.3） | 无（复用现有监听） | 中高 | 9000B 下聚合 +58%（见 5.3） |

### 5.3 实测局域网吞吐（`hub_concurrency_probe`，release，回环，256 MiB）

| 配置 | 单设备 | 说明 |
|---|---|---|
| 1452 B 载荷（旧默认） | 189~203 MiB/s | 每包一次系统调用，syscall 主导 |
| **9000 B jumbo（新默认）** | **487~597 MiB/s** | 包数降到 1/6，CPU/字节相应下降 |
| 4 条连接 @9000（单 Endpoint） | 0.69~1.10 GiB/s | 单 Endpoint 接收循环成为上限，且有 15~20% 丢包 |
| **4 个独立 Endpoint @9000** | **1.15~1.94 GiB/s** | 每 Endpoint 独立接收循环，丢包为 0 |

关键约束（实测得出）：
1. quinn 的 Cubic 初始 cwnd 为 **14720 B**，`max_udp_payload_size ≥ 14720` 会**卡死握手**；因此上限取 9000（jumbo 的标准值），绝不越界；
2. Windows 默认 64 KiB UDP 接收缓冲在 9000 B 下只够约 7 个包，**损失约 35%** —— 必须自建 socket 设 8 MiB；
3. quinn 的 `MAX_TRANSMIT_SEGMENTS = 10` 在 jumbo 下不再是瓶颈（包数已降 6 倍），**不值得 fork**；
4. 多流（B2 的分片）在 LAN 上吞吐中性（1/2/4/8 流基本持平），只对 WAN 的窗口叠加有意义；
5. DPLPMTUD 自动探测（`min_mtu=1200`），普通 1500 MTU 路径会安全降级；但**跨公网的 jumbo 价值有限**（BDP 才是 WAN 约束）。

### 5.1 实测 WAN 基线（`wan_delay_probe`，release，无损虚拟链路，稳态）

| RTT | 1.25 MB 窗口（旧默认） | 8 MB 窗口（新） | 倍数 | 实测/BDP |
|---|---|---|---|---|
| 0（回环） | 583~651 MiB/s | 692~789 | — | — |
| 40 ms | 27.4 MiB/s | **168.2** | **6.1×** | 0.88~0.92 |
| 80 ms | 13.9 | **86.3** | **6.2×** | 0.90~0.94 |
| 150 ms | 7.6 | **47.1** | **6.2×** | 0.91~0.95 |

结论：
1. **窗口就是 WAN 的绑定约束**（实测达到 BDP 的 88~95%，且 cwnd 远高于窗口，排除拥塞控制/重传/CPU）；
2. **分块大小（64K vs 256K）在传输层差异 <3%** → 原计划的"BDP 分块控制器"收益不成立，
   **从 A 阶段移除**，固定 256 KiB 即可；
3. **150 ms 时 8 MB 也接近自身 BDP**（46~47 vs 50.9）→ 要突破只能靠多流（B 阶段）；
4. 冷启动比稳态低（8 MB/150 ms：冷启 ~21 vs 稳态 46），慢启动影响明显，多流可缓解。

### 5.2 阶段 A 修订后的范围

| 项 | 状态 |
|---|---|
| 窗口 8/64/32 MiB | ✅ `6395950` |
| 删除发送端冗余哈希、worker 4→8、256 KiB 分块、超时按块缩放 | ✅ |
| fsync 策略（3.7） | ⬜ A 阶段仅剩此项 |
| ~~BDP 分块控制器~~ | ❌ 实测无收益，移除 |
| ~~per-peer 画像~~ | ⏭ 推迟到 B 阶段（画像主要价值是流数，A 阶段用不上） |

> 冷启动慢启动问题：quinn 不暴露初始拥塞窗口，应用层无法直接改；B 阶段的并行流天然
> 缓解（N 条流各自慢启动，叠加更快填满管道）。

### 5.4 阶段 C1 落地：多数据端点 + 每 peer 连接池

> 状态：已实现（`PROTOCOL_VERSION = 6`）。C2（单文件跨连接分片）仍未实现。

**范围与语义**

- `CB_QUIC_DATA_ENDPOINTS=K`：**每节点 QUIC Endpoint 总数**（控制端点 P + `K-1`
  个数据端点），默认 2，夹取 1..=4。`K=1` 时只绑定控制端点、不通告任何数据端口，
  行为与引入 C1 之前一致；线格式只多出协议版本号（空 `data_ports` 不序列化）。
- 端口规划：控制/发现端口仍是 P（mDNS 仍只广播 P）。数据端点从 `P+1` 起顺序
  分配；被占用的端口**跳过并继续向后找**（最多扫 64 个），通告的是实际绑定成功
  的端口；P 接近 65535 时停止分配（不回绕到低端口）。数据端口数少于请求数时
  按实际数量运行，全部失败则退化为单连接。
- 通告：`Hello` / `HelloAck` 增加 `data_ports: Vec<u16>`（v6）。元素语义：
  - 非 0：对端已绑定的数据端口（`P+1..`），可以对它建立独立 QUIC 连接；
  - `0`：**控制连接哨兵**（真实 UDP 端口不可能为 0），表示"用已有控制连接"。
    控制连接也占一个池槽位，池大小正好是 K，轮转后并发 peer 能铺满全部 endpoint。
  - 空列表：没有额外数据端点 / 旧对端 → 单连接。字段带
    `#[serde(default, skip_serializing_if = "Vec::is_empty")]`，旧 payload 可解码，
    空列表不写线格式。
- 轮转：控制连接的两端（server 接受顺序 / client 拨号顺序）都按本端计数器轮转
  自己通告的列表。第 n 条控制连接看到的第 0 个槽位是第 `n % K` 个 endpoint，
  于是 4 个 peer 并发时每个 peer 的第一条连接落在不同 endpoint 上。路由方向
  不固定（本仓库里 id 较小的一端拨号，因此 hub 常常是 client），两端都轮转
  才能覆盖两种拓扑。
- Endpoint 生命周期：`Transport::new` 里绑定并创建（每个 8 MiB socket 缓冲 +
  独立 `Endpoint`）；`NetManager` 为每个数据 endpoint 起一个独立 accept loop；
  `Transport::shutdown()` 置 closed 标志并 close 全部 endpoint，accept loop 据此
  退出。数据连接跑**与控制连接完全相同**的 TLS/OPAQUE/TOFU 握手，但标记为
  `SessionKind::Data`：不发 `PEER_ONLINE`/`PEER_OFFLINE`、不进 `list_peers`、
  不参与元数据广播；入站数据会话单独维护（上限 64，防未认证连接耗尽资源）。
- 连接池与分配（精确规则）：一次拉取由接收方发起（`ensure_content_cached`），
  因此池在 NetManager（发起侧）；发送方一端由连接所属的**独立 Endpoint** 承载。
  每 peer 最多 K 条连接（控制 1 + 数据 K-1），懒建立。负载 = 该连接当前活跃
  传输数（`SessionActor` 在每次状态推进后写回；按任务 C1 允许的"在途字节 /
  活跃传输数"二选一，固定取后者）。选择规则：
  1. 最不忙优先；
  2. 同负载时按 cursor 的循环距离（并发传输轮转铺开）；
  3. 未建立的数据槽位冷启动记 0（让轮转决定先连哪个 endpoint），一旦本 peer
     有过分配就记 1（让位于可复用的空闲连接，避免每次传输重新握手）；
  4. 控制连接在同负载时 +1 罚分（优先走专用数据 endpoint，控制连接只补位）；
  5. 正在建立的槽位视为满载，跳过；
  6. 全部满载 → 回退控制连接。
- **单传输只走一条连接**（不跨连接分片），多个并发传输才分散；`total_bytes <
  16 MiB`、对端未通告端口、本端 K=1 时都走控制连接。
- 失败处理：数据连接拨号/握手/建连失败只让**本次传输**回退控制连接；数据连接
  中途断开由流/会话错误让该传输失败，控制连接不受影响；下次使用时重新建连
  （死连接在预留时回收）。
- 上限：**按连接**（未改动 `SessionActor`）：8 并发 sender、8 并发 receiver、
  每传输 6 条子流、每会话 24 条子流。一个 peer 在 K 条连接下的理论上限是
  K × 8；分配层再跳过已有 8 个在途传输的连接。

**A/B 实测（release、回环、单机、4 个 Core 进程同机，256 MiB/peer）**

运行：`cargo test --release -p cb_core --test hub_concurrency_probe -- --ignored
--nocapture`，`CB_HUB_K=4`（同时扫 K=1/2/4），`CB_QUIC_DATA_ENDPOINTS=1/2/4`
交替重复。`CB_HUB_WARMUP_MB=16` 表示计时窗口前每个 peer 先拉 16 MiB，把数据连接
握手移出测量窗口（"稳态"）；默认 0（"冷启动"，即任务原始口径）。

冷启动（4 peers 同时拉 256 MiB，聚合 MiB/s）：

| D | 第 1 次 | 第 2 次 | 中位 |
|---|---|---|---|
| 1 | 908.89 | 877.12 | **893.0** |
| 2 | 895.54 | 412.57* | 654.1 |
| 4 | 827.41 | 764.77 | **796.1** |

*该次 host 抖动明显（ingest p99 164 ms、wall 2.48 s）。

稳态（预热 16 MiB 后，4 peers）：

| D | 第 1 次 | 第 2 次 | 中位 |
|---|---|---|---|
| 1 | 727.47 | 713.23 | 720.4 |
| 2 | 839.26 | 886.21 | **862.7** |
| 4 | 421.45* | 791.72 | 606.6 |

*该次 wall 2.43 s（4 个 peer 各自 elapsed 仅 ~1.09 s），同样是 host 抖动。

`CB_HUB_K=2`（2 peers × 256 MiB）冷启动中位：D=1 608、D=2 681、D=4 550；
稳态中位：D=1 412、D=2 584、D=4 488。

端点利用证据（日志中每连接一行；临时 trace 已删除，正式代码保留 log_sink）：

- D=4 稳态（干净的一次）：预热后 3 个数据连接分别落在 hub 的 52908/52909/52910，
  第 4 个 peer 走控制连接哨兵；测量阶段 4 个 peer 每个 256 MiB、`verified=true`，
  即 4 个 endpoint 各承载 1 个传输。
- D=2 稳态：hub 数据端口 59321 承载 2 个 peer（2 × 256 MiB），控制连接承载另外
  2 个 peer（2 × 256 MiB），两个 endpoint 都被使用。
- 冷启动 D=4：hub 端口 51943/51939/51935 + 控制连接，共 4 个 endpoint。
- 所有轮次：`PEER_OFFLINE=0`、`TRANSFER_FAILED=0`、`CORE_ERROR=0`，
  `list_peers` p99 < 1 ms；ingest p50 1.3~2.4 ms（个别轮次 p99 有明显 host 抖动）。

**结论（诚实）**：多 endpoint 的负载分摊**已验证生效**，但在本机同进程/多 Core
的单机 A/B 里**没有测到可复现的聚合提升**：冷启动下 D=2/4 反而略低（首个大传输
要付数据连接握手）；稳态下 D=2 有 +18~46% 的迹象，D=4 不一致（一次异常慢）。
per-peer 速率在所有配置下都是 220~310 MiB/s，与 endpoint 数无关，说明瓶颈不在
发送侧 endpoint 接收循环，而在**单机共享的应用层 CPU/传输任务**（hub 与 4 个 peer
的 5 个 Core 都在同一台机器上，每个 NetManager 8 个 worker）。ADR §5.3 的 +58%
来自两侧各 4 个独立 Endpoint 的纯 QUIC 探针（CPU 足迹远小于本应用）；本应用在
这种单机拓扑下尚未触及那个上限。跨设备部署（每个 peer 独立 CPU）时预期收益
应更接近 §5.3，需要在多机环境复测。

### 5.4.1 C2 仍需要什么

1. **同一条传输跨多条连接**：把 `ContentBegin.ranges` 按连接数再切分，并让
   `TransferHeader` 携带"该区间走哪条连接/哪条流"的路由信息；接收端的
   `ReceiverRanges` 需要支持来自不同 `SessionActor`（不同 Connection）的区间，
   即跨会话共享一个传输注册表（当前 receiver 状态是会话私有的）。
2. **发送侧主动分片**：当前是接收方选择连接；C2 需要发送侧按连接空闲度动态
   分配区间，或由接收方在 `ContentGet` 中按连接声明 `(offset,length)`。
3. **失败重调度**：某条连接失败时，把未完成区间重新分配到其它连接（现有
   B2 的 3 次重试是单连接内的流级重试）。
4. **连接数控制器**：§4.3 的"开第 2 条连接并观察收益"需要按传输聚合 goodput
   的采样窗口；C1 只实现了静态 K 上限 + 懒建立。
5. **控制面协调**：区间计划目前只在一端生成；C2 需要把"跨连接区间计划"放进
   `ContentBegin`（或新增消息），并保证两端的校验/取消语义一致。


每个阶段都必须能被现有 `hub_concurrency_probe` 验证；阶段 B/C 需要**新增 RTT 模拟**
（本地 UDP 延迟代理）才能测 WAN 档，否则只有回环数据。

## 6. 验证计划

1. **LAN（回环）**：现有 `hub_concurrency_probe`，K=1/2/4，256 MiB，对比吞吐、粘贴延迟、掉线；
2. **WAN 模拟**：写一个本地 UDP 转发代理，注入 40/80/150 ms RTT 与 0.1% 丢包，
   把 Core 的 peer 地址指向代理；测每档吞吐与自适应切换是否正确（不抖动）；
3. **续传**：传输中途 kill 接收端，重启后验证从已完成偏移续传；
4. **fsync 策略**：断电/强杀测试（模拟：进程结束后立即断电不可行，改为比对
   `durable` 标记与文件实际落盘）；
5. **回归**：ingest 延迟 p99 不得劣化（当前 2.3 ms 量级）。

### 5.4.2 默认值决策（2026-11-06）

C1 在单机回环上用 `CB_QUIC_WORKERS` 做了 CPU 非饱和对照：探针全程只用 5~7/32 核，
多端点仍无可复现收益（D=4 仅 +6~9% 且配对胜负 6/12，默认 worker 下 D=1 最好），
而每条数据连接要多付一次 OPAQUE 握手、公网端口可能不可达（每个大传输最多多等 ~8s 才回退）。
因此 **`CB_QUIC_DATA_ENDPOINTS` 默认改为 1（单端点，等于引入多端点前的行为）**，
多端点保留为实验开关，等 10G 真机 + C2（单文件跨连接分片）再评估。
